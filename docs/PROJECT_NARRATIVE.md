# Project Narrative: Multimodal Affect Recognition Suite

**Author:** Burhanuddin Mustafa
**Document type:** Project narrative and engineering retrospective
**Status:** Complete (v1.0)
**Related documents:** `README.md`, `docs/decisions.md`, `docs/flow.md`, `docs/SELF_REVIEW.md` (pending)

## 1. Origin and Motivation

This project began as a dormant repository — `ck_emotion_analyzer`, an old prototype built around the CK+ dataset, abandoned long enough that its own author had largely forgotten what state it was in. Auditing it before deciding whether to continue it revealed it was not a working system with rough edges, but an unfinished sketch: a training notebook that built a model and printed `.summary()` but never called `.fit()`; a Flask inference route resizing images to 224×224 against a model trained at 100×100; a saved-checkpoint filename that didn't match what the inference code tried to load; a webcam frontend posting JSON to an endpoint that expected multipart form data; and no face-detection step at all, meaning even a working model would have been classifying raw, uncropped webcam frames against a model trained exclusively on tightly-cropped lab photographs.

The decision made at that point shaped everything that followed: not to patch this into a barely-working demo, but to rebuild it properly and, critically, to decide *what it was actually for* before writing new code. A facial-expression classifier is a commodity capability on its own — the guiding question became what larger system this component could genuinely serve, given an existing portfolio of assistive BCI projects (`bci-speller`, `mi-bci-pipeline`, and others) already addressing adjacent problems. That question is answered explicitly in §3, and shaped the eventual scope: not just a facial classifier, but a multimodal suite pairing it with an EEG-based affect channel on shared ground.

## 2. Research Backing

The project draws on established work in two separate domains, combined rather than treated as one:

- **Facial expression datasets**: FER2013 (Goodfellow et al., 2013) and its FER+ relabeling (Barsoum et al., 2016) as the public model's training data — chosen specifically because neither carries the redistribution/commercial-use restrictions that AffectNet, RAF-DB, and DREAMER do. AffectNet and RAF-DB were used for cross-dataset validation only, never training, for exactly that licensing reason.
- **Facial model architecture**: MobileNetV2 (Sandler et al., 2018), ImageNet-pretrained, fine-tuned in two phases (frozen backbone, then partial unfreeze) — standard transfer-learning practice for a moderate-sized dataset, chosen directly in response to the original prototype's from-scratch CNN never having been trained at all.
- **EEG dataset**: DREAMER (Katsigiannis & Ramzan, 2018) — 23 participants, 14-channel Emotiv EPOC EEG, valence/arousal/dominance self-report labels — selected after the originally-planned DEAP dataset's official host was confirmed discontinued (see §4.2).
- **EEG model architecture**: EEGNet (Lawhern et al., 2018), ported directly and unmodified from the [`mi-bci-pipeline`](https://github.com/BurhanxGodhra/mi-bci-pipeline) project's own implementation — an architecture already validated on a different EEG task (motor imagery) in that prior project, reused here for affect classification since its channel/timepoint parameterization is dataset-agnostic by design.
- **Real-time streaming**: Lab Streaming Layer (LSL), the de facto standard protocol for real-time neurophysiological data — chosen so that a real headset and a simulated/replayed data source could be architecturally indistinguishable to every downstream component (see §4.8, and `docs/decisions.md` D-011).
- **Hardware bridging**: BrainFlow, a single library exposing a unified API across many consumer/research EEG boards (OpenBCI, Muse, and others), used in preference to per-vendor SDKs specifically to avoid a one-headset-at-a-time integration strategy.

## 3. Value Proposition and Industry Standing

Stated plainly, because it would otherwise only be implied: **a facial-expression classifier has limited value standing alone.** Detecting "this face looks happy" from a webcam is a commodity capability available in numerous existing libraries and products. Building one from scratch is only worth the effort if it becomes a component inside something that needs it specifically — and that "something" was decided deliberately, not left as an open question for a reader to guess at.

The concrete answer: this suite is designed to sit alongside `bci-speller` and `mi-bci-pipeline` as an **affective context layer**. A BCI speller communicates *what* someone typed; it says nothing about *how they're doing* while typing it, and for augmentative-communication users with severe motor or speech impairment, that emotional context is frequently as important as the literal words. Beyond that framing, three further concrete integration points were identified: the fused affect estimate as a feedback signal another BCI system could act on (detected frustration triggering a simplified interface); a fallback expressive channel for when the primary EEG-based control signal is unreliable — the specific and only reason the Accessibility Mode page exists; and, more structurally, the calibration methodology built here (personalizing a generic, poorly-cross-subject-generalizing model using a cheap proxy label) as a pattern reusable across the rest of the BCI portfolio, not a feature specific to affect classification.

No independent, third-party review of this project has been conducted as of this writing. A rigorous internal self-assessment is planned as a separate document (`docs/SELF_REVIEW.md`) rather than folded into this narrative, consistent with treating that kind of critical accounting as substantial enough to warrant its own space — but it should not be assumed complete or exhaustive in its absence. One concrete gap already known and worth stating here rather than waiting for that document: the integration story in this section is a documented architectural intention, not yet wired into working code — `bci-speller` and this suite do not currently exchange any data (see README Roadmap).

## 4. Build Journey

### 4.1 Phase 1 — Repository Archaeology and the Rebuild Decision

The existing repository was audited file-by-file before any new code was written, specifically to catalogue what was actually broken rather than assume the prior effort was close to working. This surfaced the specific list of defects described in §1, all independently verifiable in the notebook and scripts as they stood. The decision to fully rebuild — new data pipeline, new architecture, new inference stack — rather than patch forward from this state was made once it was clear the prototype had never reached a working end-to-end path at any point in its history, not merely regressed from one.

### 4.2 Phase 2 — Dataset Acquisition and Licensing Reality

FER2013 downloaded cleanly from Kaggle with no complications. AffectNet and RAF-DB both required manual, human-reviewed access requests — RAF-DB's request was still pending approval when an unrelated Kaggle download, downloaded under the filename `ferplus`, turned out on closer inspection to already *be* RAF-DB: its numeric folder structure's per-class sample counts summed to exactly 12,271, matching RAF-DB's published training-set size, with per-class counts matching its known distribution closely enough to rule out coincidence. This was confirmed by cross-referencing counts, not by trusting the filename — the actual Microsoft FER+ dataset (vote-distribution relabeling of FER2013) was never in hand at all, a distinct dataset from what this download's name implied.

AffectNet's own labels.csv was found, on inspection, to disagree with the folder each image had been filed under for at least some images — evidence the folder reflected an earlier or different labeling pass than the CSV's `label` column, which also carried a `relFCs` confidence score suggesting an automated relabeling process. The CSV was adopted as ground truth, with a confidence-threshold filter, rather than trusting folder placement.

DEAP, the dataset originally planned for the EEG/calibration side specifically because it includes synchronized facial video, was found to have a discontinued official host partway through this phase — a `scicrunch.org` resource record explicitly marked "no longer in service." This was not a workaround-able problem; DREAMER was adopted in its place, at the cost of losing DEAP's synchronized-video advantage for the calibration page's design (see §4.7 and README Limitations).

### 4.3 Phase 3 — Facial Model Training

MobileNetV2 transfer learning was trained in two phases (frozen backbone, then partial fine-tuning), producing an initial 61.2% test accuracy — a reasonable baseline given FER2013's well-documented label noise (human inter-annotator agreement on FER2013 itself sits around 65-68%). A follow-up retrain intended to improve this via data augmentation instead collapsed accuracy to 29.7%, with training never exceeding random chance in its first phase. The cause, once traced, was a genuine implementation bug rather than a hyperparameter issue: `RandomBrightness` and `RandomContrast` layers were being applied *after* `preprocess_input`'s normalization to a `[-1, 1]` pixel range, while those layers' default behavior assumes standard `0-255`-range images — the mismatch clipped nearly every training image to its extremes for the entire run.

This incident also exposed a second, structural problem: the training script always saved to the same fixed model path, meaning this regressed run had silently overwritten the previous, working 61.2% model on disk with no backup. Both issues were corrected together: augmentation was moved to run before normalization (the actual fix), and the training script was changed to save every run to its own timestamped folder, only promoting a run to the "production" model path if it beats the previously recorded best test accuracy (see `docs/decisions.md` D-006, D-007). The corrected pipeline retrained to 67.4% — beating the original baseline, not merely recovering from the regression.

### 4.4 Phase 4 — Inference Pipeline and Face Detection Churn

Building live inference required detecting and cropping faces from raw webcam frames before classification — the specific step missing from the original prototype. Three separate face-detection approaches were attempted in sequence before one worked, for reasons unrelated to this project's own code: the installed `opencv-python` build's legacy `cv2.CascadeClassifier` API (Haar cascades) was unavailable, apparently removed in a version of OpenCV newer than most existing tutorials assume; MediaPipe's newer Tasks-based face detector loaded successfully but crashed at inference time with a Metal/GPU service initialization failure on macOS, confirmed via testing to persist even when a CPU delegate was explicitly forced — a known upstream platform issue rather than something addressable from calling code. OpenCV's own YuNet detector (`cv2.FaceDetectorYN`), a currently-maintained, ONNX-based detector, worked immediately once its model file was downloaded.

The standalone webapp (webcam capture via `getUserMedia`, periodic frame POST to a FastAPI `/predict` endpoint) was then built and wired to this corrected pipeline, along with a ~15% padding margin added around each detected face box — closing a mismatch between YuNet's tight bounding boxes and the somewhat looser crop margins present in the training datasets.

### 4.5 Phase 5 — Packaging and Environment Friction

Both `emotion_analyzer` and, later, `bci_suite` failed their first `pip install -e` attempt with an identical error: setuptools' automatic package discovery refused to proceed because each project's root directory contained multiple plausible top-level packages (the actual code package, alongside sibling folders like `webapp/`, `notebooks/`, or `pages/`). Both were fixed identically, by adding an explicit `[tool.setuptools.packages.find] include = [...]` directive naming only the real package. Separately, a `.gitignore` written to exclude `.venv/` failed to exclude the actually-created `venv/` (no leading dot) — a naming mismatch that would have committed an entire virtual environment's contents had it gone unnoticed before the first push. A recurring, lower-stakes friction throughout this phase and beyond was downloaded files retaining their descriptive download filenames (`eeg_loaders.py`, `bci_suite_pyproject.toml`) rather than being renamed to what Python's import system or `pip` required (`loaders.py`, `pyproject.toml`) — a mistake repeated several times across the project despite being flagged each time it occurred.

### 4.6 Phase 6 — BCI Suite Scaffold and the EEG Model

With EEGNet ported unmodified from `mi-bci-pipeline` (see §2), a DREAMER-specific data loader was written against the dataset's documented `.mat` structure and worked correctly on its first run against the real downloaded file — a contrast to the facial dataset phase, where every dataset needed at least one round of correcting an incorrect assumption. Initial training used a plain random train/test split across all extracted 4-second windows, producing 44.4% test accuracy with visibly erratic validation accuracy between epochs (swinging between roughly 0.05 and 0.44). The cause was leakage: windows chunked from the same ~60-second trial are highly correlated, and a random split let windows from one trial appear in both training and test data, letting the model partially recognize trials it had already seen slices of. Correcting this to a participant-level split (`GroupShuffleSplit`, ensuring no participant's data crosses between train/val/test) produced a more honest — and, notably, slightly *higher* — 48.6% cross-subject test accuracy on 5 held-out participants, against a 25% chance baseline for the 4-class task.

A separate, minor issue surfaced at export time: the trained PyTorch model's ONNX export crashed on a missing optional dependency (`onnxscript`, required by PyTorch's newer export path for the requested opset version), resolved with a fallback to the older exporter when that dependency isn't present.

### 4.7 Phase 7 — The Circular-Logic Critique and Calibration Redesign

The first working versions of the Calibration and Fusion pages displayed each sampled EEG window's true DREAMER label directly in its selection dropdown — e.g., "participant 10, true label: Excited/Happy" — before any prediction was run. This was identified as a fundamental design flaw not during development, but by the project owner reviewing the running application: showing the answer before asking the question makes "prediction" meaningless, and a "calibration" page that only displays a static side-by-side comparison, with no accumulated record and no downstream consequence, does not actually calibrate anything. This is recorded here specifically because it was an internal-review gap — the flaw existed through an entire working, bug-free version of both pages before being caught by external critique rather than by the person who built it.

The redesign that followed did more than hide the label: it gave calibration an actual function. Each facial snapshot now auto-pairs with whatever EEG window is live at that moment (logged automatically, no separate manual action), accumulating toward a user-set target count with progress tracking and guidance on a reasonable target size. Reaching that target unlocks fine-tuning a personalized model from the collected pairs (`personalize.py`), saved under a user-chosen name and selectable later on the Fusion page alongside the generic model — turning a passive display into the actual calibration workflow the page's name had always implied but not delivered.

### 4.8 Phase 8 — Live Streaming Architecture

To support the newly-functional calibration workflow with a real signal source, an LSL-based streaming layer was built in two matched pieces: `replay.py`, which streams a DREAMER trial over LSL to simulate a headset, and `stream.py`, a generic LSL reader with no awareness of whether its source is real hardware or a replay. This paid off directly when real-hardware support (`brainflow_bridge.py`, using BrainFlow to bridge OpenBCI/Muse-family devices to the same LSL interface) was added afterward without any change to `stream.py`, `stream_launcher.py`, or the page logic consuming them.

A channel-matching refinement — selecting and reordering electrodes by name rather than only checking raw channel count, so a headset with more than 14 channels could still work if it includes the 14 required positions — surfaced a genuine LSL API subtlety during testing: `pylsl.resolve_byprop()` returns a lightweight stream descriptor that does not include custom metadata such as channel labels; the full descriptor, including labels published by `replay.py`/`brainflow_bridge.py`, is only available after opening an inlet and querying its `.info()`. The first implementation read labels from the lightweight object, always found none, and silently fell back to a count-only check — diagnosed and fixed once traced to this specific API behavior. Separately, starting and stopping these streams was moved from requiring a manually-opened second terminal to in-app Start/Stop buttons launching and terminating the same scripts as managed subprocesses.

### 4.9 Phase 9 — Documentation and the Integration Question

With both models trained, live streaming working, and calibration functioning end-to-end, the last explicit step taken before considering the project complete was to answer, in writing, the question posed at the very start in §1: what does this actually integrate into, and does that answer hold up. That question, and its answer, are recorded in full in §3 rather than left as an implicit assumption — a deliberate final step, not an afterthought.

## 5. Findings and Results

**Facial emotion classifier:** 67.4% test accuracy (MobileNetV2, FER2013 + FER+ + RAF-DB + AffectNet-with-confidence-filtering, held-out test set), recovered and improved from a mid-project regression to 29.7% caused by an augmentation-ordering bug (§4.3).

**EEG affect classifier:** 48.6% cross-subject test accuracy on 5 DREAMER participants never seen during training (4-class valence/arousal quadrant task, chance = 25%), corrected from an initially leakage-inflated 44.4% by moving to a participant-level train/test split (§4.6).

**Streaming architecture:** validated end-to-end against a replayed DREAMER stream, including real-time channel-name matching; not yet validated against physical EEG hardware (see README Limitations).

**Calibration/personalization pipeline:** functionally complete and exercised end-to-end (live pairing, progress tracking, fine-tuning, saving, model selection), but only against a live user's facial expressions paired with a *replayed* single DREAMER trial from a different, unrelated person — an honestly mismatched calibration set, not a stand-in for genuine synced hardware data (see README Limitations).

## 6. Self-Assessment (Preliminary)

A full, dedicated self-review is planned separately (`docs/SELF_REVIEW.md`) and should be treated as the authoritative critical account once written. Provisionally, the most significant finding worth surfacing here is the one described in §4.7: a genuine, fundamental design flaw (displaying ground truth before prediction) existed through a complete, functioning version of two major pages before being caught — by external critique, not internal review. That gap in this project's own review process is itself worth treating as a finding, not just the bug it produced.

## 7. Closing Assessment

The project moved from an abandoned, never-functional prototype to two independently trained and honestly evaluated models, a working live-streaming architecture built to be hardware-agnostic by construction, a calibration workflow with genuine function rather than a passive display, and a stated, specific answer to the question of what this system is actually for. Several of its most valuable moments came from things going wrong and being fixed rather than going right on the first attempt — a mislabeled dataset, a training regression, a face-detection library that crashed for platform reasons outside this project's control, a leaked evaluation split, and a circular-logic design flaw caught only by outside review. Each is recorded here and in `docs/decisions.md` on the same standard: report what was measured, explain why, and state plainly what remains unresolved.
